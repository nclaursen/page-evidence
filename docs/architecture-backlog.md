## Original critical findings — C1/C2 resolved on 16 October 2026

### C1. Persisted snapshots do not bind to site/property/configuration

- **Evidence:** `snapshotId()` in [core.ts](../src/core.ts) uses profile/provider/period. `sync()` in [service.ts](../src/service.ts) reuses a fresh saved payload without checking domain, GSC property, analytics property/site, tracking policy, or retrieval limits. Snapshot payloads omit those connection identities. History matches profile/provider/window; action rows have no profile/site column and rely on private directory isolation.
- **Impact:** reconfiguring an existing profile/data directory for another site or property can return earlier-site evidence under the current connection context. Shared directories are already prohibited; even separate Umbraco/personal directories do not protect a repurposed profile. Sanitized profile-name collisions are an additional reason not to treat the ID as a full identity key.
- **Proposed scope:** bind stored evidence to a non-secret connection/configuration fingerprint, validate before reuse/history/review, and define safe handling of legacy payloads/state. Retain separate directories; do not introduce multi-tenancy to solve this.
- **Acceptance:** synthetic site/property changes cannot reuse or relabel old evidence; both representative instances retain comparable history; legacy migration/invalidation behavior is documented and tested. No credential material enters the fingerprint/output.

### C2. General page keys can collapse different hosts

- **Evidence:** `normalize()` in [core.ts](../src/core.ts) returns only path/query. `sync()`, `pageContext()`, history/review matching in [service.ts](../src/service.ts), and Engage aggregation use that key. The external opportunity engine separately uses host-preserving `sitePageKey()` in [search-opportunities.ts](../src/search-opportunities.ts).
- **Impact:** a domain-level GSC property with root/subdomain pages sharing a path can select/associate the wrong page or combine analytics evidence. A foreign URL with the same path can match page context. This can affect any instance, especially a multi-site organization; the newer external-search path already handles scope more carefully.
- **Proposed scope:** agree one site/host-aware page-identity policy for common matching and adapter aggregation, retaining meaningful query/case/slash semantics. Treat persisted-key changes as a migration decision.
- **Acceptance:** root/www policy is explicit; distinct subdomains and foreign hosts do not silently collide; GSC/analytics/history/actions retain correct associations across both instance types.

## Audit verification and use

The documentation task verified source/path/script references, nested Git scope, Claude imports, instruction consistency, and unchanged application-file hashes. Synthetic probes of the existing `snapshotId()` and `normalize()` bodies confirmed the identity/key collisions underlying C1/C2 without provider calls or application storage. No application code, credentials, configuration, or functionality was changed. Package tests were inspected for coverage; the application test suite/build and live integration checks were not run for this documentation-only change. Record implementation checks and live validation in the relevant future plan.

For an approved improvement, start with its evidence and acceptance criteria, apply the five placement questions, inspect current contracts, save a concise plan for substantial work, and validate the affected provider/instance matrix. An item is complete only when its required behavior and compatibility/migration evidence are verified; documentation alone does not close it.
